Planned approach

Four decisions that shape everything else.

It measures

Every card has a collector behind it. pnpm collect region-latency writes rows; the card reads them. No glue.

A card is one folder

cards/<id>/ holds the component, the dataset query, the collector and the explainer. Four files and one line of config.

Zero keys on day one

Region latency, SEO audits and releases need no API keys. Three datasets are live about ninety seconds after pnpm setup.

You own the data

One Postgres schema, plain SQL, no ORM, no vendor. DROP SCHEMA atlas CASCADE is a clean uninstall.

Planned card anatomy

One card is one folder.

A card is not smeared across a route file, a barrel, an info map and an anchor constant. It is a directory and one call to defineCard().

cards/region-latency/
cards/
└── region-latency/
    ├── cards.tsx     the component
    ├── dataset.ts    the SQL it reads
    ├── collector.ts  what fills the table
    └── info.ts       what it means
cards.tsx
export default defineCard({
  id: "region-latency",
  title: "Region latency",
  category: "performance",
  span: 2,
  dataset: "region-latency",
  collector: "region-latency",
  info,
  component: () => import("./view"),
  requires: (env) => env.site.url,
  optIn: false,
})

A card whose requires is not met stays on the grid and says why, rather than vanishing. Cards you don't need are one line in atlas.config.ts to disable.

Nine groups, and the collector behind each.

Configuration is one file, atlas.config.ts at the repo root: your site URL, which cards are enabled, and any overrides. The database is one variable, DATABASE_URL.

Planned collectors

Six collectors, three ways to run them.

pnpm collect <id>, POST /api/collect/<id>, or cron. Every run is wrapped in a collector_runs row, so freshness on the cards is measured, not assumed — and a second run says “already running” instead of double-firing.

region-latency

~15s

TTFB probes from a dozen regions, via Globalping.

Needs nothing — free and keyless.

seo-audit

~60s

Per-page audit findings and score history.

Needs your site URL.

lighthouse

~15min

Scores and Core Web Vitals, route by route.

Needs a PageSpeed key — optional.

releases

~10s

Deploy cadence and what shipped when.

Needs a GitHub repo.

repo-metrics

~4min

Duplication, complexity and dependency health.

Needs a checkout of the repo.

ai-usage

~5s

Token spend across coding-agent CLIs.

Needs the local machine — opt-in.

Zero keys on day one. Region latency, SEO audits and releases need no API keys at all — three datasets are live about ninety seconds after pnpm setup. Errors, web vitals and page views have no collector: they are push-ingested by a beacon.

Your data, your box

A schema, not a database.

Atlas creates one Postgres schema — atlas by default — so it can live inside a database that already has two hundred tables without colliding with any of them. Plain SQL, no ORM, no vendor. DROP SCHEMA atlas CASCADE is a clean uninstall.

Three planned auth adapters

open
The default, so pnpm dev works with no configuration. It refuses to serve in production — the app boots to the setup screen instead of quietly exposing your telemetry.
password
One shared password. No extra table, no extra dependency, and the out-of-the-box answer for a small self-hosted deployment.
header
A trusted identity header, for running behind Cloudflare Access, oauth2-proxy, Authelia or Tailscale — where the gateway has already done the authenticating.

Collectors are triggered with a session or a bearer secret, so a cron sidecar can refresh a card without a browser anywhere in the picture.
